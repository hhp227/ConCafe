# 🎀 ConCafe UI 구조 설계 문서

## 📱 1. 하단 탭 구조 (Bottom Navigation)
[홈]  [탐색]  [체크인]  [랭킹]  [내 정보]

### 메인 네비게이션 노출 규칙
- 게스트 또는 일반 유저(`VISITOR`) 로그인 상태:
  - [홈] [탐색] [체크인] [랭킹] [내 정보]
- 캐스트(`CAST`) 로그인 상태:
  - [홈] [탐색] [팬관리] [랭킹] [내 정보]
- 카페 운영자(`CAFE_OWNER`) 로그인 상태:
  - [홈] [탐색] [카페관리] [랭킹] [내 정보]
- 관리자(`ADMIN`) 로그인 상태:
  - [홈] [탐색] [운영관리] [랭킹] [내 정보]

### 역할별 탭 치환 원칙
- 세 번째 메인 탭은 기본적으로 `체크인` 영역이다.
- 로그인한 사용자 역할이 `CAST`이면 `체크인` 탭 대신 `팬관리` 탭을 노출한다.
- 로그인한 사용자 역할이 `CAFE_OWNER`이면 `체크인` 탭 대신 `카페관리` 탭을 노출한다.
- 로그인한 사용자 역할이 `ADMIN`이면 `체크인` 탭 대신 `운영관리` 탭을 노출한다.
- 게스트와 일반 유저는 항상 `체크인` 탭을 사용한다.
- 한 계정에 여러 역할이 공존하는 경우 우선순위는 `ADMIN > CAFE_OWNER > CAST > VISITOR`로 적용한다.

### 카페/캐스트 상세 진입 정책 (2026-03-19 업데이트)
- 메인 탭의 `홈`, `탐색`, `체크인`, `랭킹`, `내 정보`에서 카페 상세/캐스트 상세 진입은 로그인 사용자만 가능하다.
- 비로그인 사용자가 카페/캐스트 카드를 탭하면 네비게이션은 차단하고 로그인 유도 Dialog/Alert를 노출한다.
- 로그인 유도 Dialog/Alert의 기본 액션은 `로그인`(SignIn 이동) / `취소`다.

### 구현 정합성 메모 (2026-03-22)
- 런타임 앱 데이터소스는 `FirestoreConCafeDataSource` + Firebase Auth/Firestore/Storage REST 경로를 사용한다.
- `MockConCafeDataSource`는 현재 `shared/src/commonTest` 테스트 전용으로만 남아 있고 앱 런타임에서는 사용하지 않는다.
- 세션 복원은 3플랫폼 공통으로 `restoreSession` + `observeCurrentUser` 조합으로 동작한다.
- 지도는 Android(Compose GoogleMap), iOS(Apple Map), Desktop(Google Maps JavaScript WebView)로 분기 구현되어 있다.
- `운영관리`의 승인 대기 목록은 Firestore pending claim 조회 경로를 사용한다.

# 1️⃣ 🏠 홈 (Home)

### 목적
- 앱 진입 시 첫 화면
- 관심 메이드 & 인기 정보 노출

### UI 구성
- 상단: 로고 + 알림 아이콘
- 🎀 홈 프로모션 배너 (상단 캐러셀)
- 🔥 인기 캐스트 (가로 스크롤 카드)
- 📍 근처 메이드카페 (지도 미리보기 또는 카드 리스트)
- 🎂 생일인 메이드
- 📢 카페 공지 (최근 3개)

### 현재 구현 메모
- `인기 캐스트` 섹션은 홈 피드에서 1페이지 10개씩 가져오며 `더보기`로 다음 페이지를 이어 붙인다.
- 홈 인기 캐스트 최대 노출 상한은 현재 mock 데이터소스 기준 50개다.
- `근처 메이드카페`도 동일한 cursor 기반 페이지네이션으로 추가 로드한다.

### 홈 배너 노출 정책
- 홈 상단에는 프로모션 배너를 캐러셀 형태로 노출한다.
- 동시에 노출되는 활성 배너는 최대 5개로 제한한다.
- 배너마다 노출 시작일과 종료일이 있으며, 현재 시간이 노출 기간 안에 있을 때만 홈에 표시된다.
- 활성 배너 슬롯이 모두 찬 상태에서는 신규 배너를 즉시 게시할 수 없고 예약 등록만 가능하다.
- 예약 배너는 기존 활성 배너 종료 이후 순차적으로 노출된다.
- 현재 구현에서는 홈 피드 조회 시 종료된 활성 배너를 정리하고, 빈 슬롯 수만큼 `SCHEDULED` 배너를 `ACTIVE`로 자동 승격한다.

### 홈 배너 등록 권한
- 관리자(`ADMIN`)는 전체 홈 배너를 등록/수정/중지할 수 있다.
- 카페 운영자(`CAFE_OWNER`)는 본인이 운영 권한을 가진 카페 관련 배너를 등록할 수 있다.
- 일반 유저와 캐스트는 홈 배너를 등록할 수 없다.

### 홈 배너 카드 요소
- 배너 이미지
- 제목
- 서브 문구
- 연결 대상 (카페 상세 / 이벤트 / 외부 링크 등)
- 노출 기간
- 등록 상태 (`DRAFT`, `SCHEDULED`, `ACTIVE`, `ENDED`, `PAUSED`)

# 3️⃣ 📍 체크인

### 메인 화면
- 현재 위치 기반 카페 지도
- 오늘 방문한 카페
- + 방문 추가 버튼
- 최근 방문 타임라인

### 공통 지도 원칙
- 체크인 탭의 지도는 로그인 여부와 관계없이 공통으로 노출한다.
- 비로그인 상태에서는 지도 탐색만 허용하고 카페/캐스트 상세 진입은 로그인 유도 후 허용한다.
- 로그인 상태에서는 같은 지도를 유지한 채 실제 체크인 액션과 방문 기록 기능을 확장한다.
- 즉, 로그인 여부에 따라 사라지는 것은 지도가 아니라 `체크인 가능 범위`다.

### 체크인 플로우
1. 카페 선택
2. 날짜 선택
3. 위치 인증 (100m 반경)
4. 메모 작성
5. 등록

### 체크인 후 리뷰 유도 UX
- 체크인 완료 직후 `리뷰를 작성하면 어떠세요?` 바텀시트를 노출한다.
- 버튼은 `지금 작성`, `나중에`로 구성한다.
- `지금 작성`을 누르면 해당 카페의 리뷰 작성 화면으로 이동한다.
- `나중에`를 누르면 같은 `visitId` 기준으로는 반복 노출하지 않는다.
- 이미 해당 방문 기준 리뷰를 작성한 경우에도 다시 노출하지 않는다.

### 노출 대상
- 게스트
- 일반 유저(`VISITOR`)

### 체크인 탭 - 비로그인 사용자 화면

#### 목적
- 로그인하지 않은 사용자도 ConCafe의 핵심 콘텐츠인 메이드 카페 정보를 계속 탐색할 수 있도록 한다.
- 체크인 기능은 로그인 후에만 사용할 수 있도록 제한하되, 공통 지도와 인기 카페/캐스트 정보는 자유롭게 확인 가능해야 한다.

#### 화면 구성
- 비로그인 상태에서 체크인 탭에 진입하면 아래 UI를 표시한다.
- 단, 상단 지도 영역은 로그인 상태에서도 동일한 구조를 유지한다.

##### (1) 카페 지도 (Map)
- 현재 위치 기반 지도를 표시한다.
- 주변 메이드 카페 위치를 마커로 표시한다.
- 마커를 탭하면 카페 상세 화면으로 이동할 수 있다.
- 지도 내 `체크인` CTA를 누르면 로그인 유도 BottomSheet를 노출한다.

##### (2) 인기 메이드 카페 섹션
- 제목: `🔥 인기 메이드 카페`
- 표시 정보:
  - 카페 이름
  - 위치
  - 평점
  - 총 체크인 수
- 정렬 기준:
  - `checkinCount` 내림차순
- 표시 개수:
  - 최대 10개

##### (3) 인기 캐스트 섹션
- 제목: `☕ 오늘 인기 캐스트`
- 표시 정보:
  - 캐스트 프로필 이미지
  - 캐스트 이름
  - 오늘 방문 수
- 정렬 기준:
  - `todayVisit` 내림차순
- 표시 개수:
  - 최대 10명

##### (4) 로그인 유도 영역
- 문구:
  - `로그인하고 메이드카페 방문을 기록해보세요!`
- 혜택 안내:
  - 방문 기록 저장
  - 카페 팬 레벨 상승
  - 체크인 배지 획득
- 버튼:
  - 로그인
  - 회원가입

#### 기능 제한
- 비로그인 사용자 가능 기능
  - 지도 탐색
  - 카페 정보 보기
  - 캐스트 정보 보기
  - 인기 카페 확인
- 비로그인 사용자 제한 기능
  - 체크인
  - 리뷰 작성
  - 좋아요
  - 팬 레벨

#### 로그인 유도 BottomSheet
- 비로그인 사용자가 체크인 버튼을 누르면 로그인 유도 BottomSheet를 표시한다.
- 메시지:
  - `체크인하려면 로그인이 필요합니다.`
- 버튼:
  - 로그인하고 체크인
  - 회원가입

### 체크인 탭 - 로그인 사용자 화면 방향
- 로그인 상태에서도 체크인 탭 상단에는 동일한 지도 영역을 유지한다.
- 로그인 사용자는 지도에서 카페를 탐색한 뒤 실제 체크인 플로우로 진입할 수 있다.
- 인기 메이드 카페 / 인기 캐스트 섹션은 유지하거나 하단 보조 섹션으로 재배치할 수 있다.
- 오늘 방문 / 최근 타임라인은 지도 아래에서 확장 정보로 노출한다.

# 3-1️⃣ 🎀 팬관리

### 목적
- 캐스트가 팬과의 접점을 관리하는 전용 탭

### 메인 화면
- 내 프로필 요약
- 팔로워 수
- 출근 일정 바로가기
- 팬 대상 공지/알림 관리
- 소속 카페 대시보드 바로가기
- 캐스트 프로필 연결 상태 확인

### 노출 대상
- 캐스트(`CAST`)

### 캐스트 프로필 연결 원칙
- 캐스트는 회원가입 시 소속 카페를 선택한다.
- 기존 캐스트 프로필이 있는 경우 캐스트는 `팬관리`에서 본인 프로필 연결 요청을 보낸다.
- 연결 요청은 팬관리 내부 전용 신청 UI에서 처리하며, 운영자용 대시보드로 진입시키지 않는다.
- 연결 요청이 `PENDING`이면 팬관리에서 `승인 대기 중` 상태를 표시한다.
- 운영자는 `카페 관리 대시보드 > 캐스트 관리 섹션` 상단에서 요청을 검토하고 승인 / 반려한다.
- 승인되면 해당 캐스트 문서의 `linkedUserId`가 현재 유저 id로 연결된다.
- 연결된 캐스트 프로필이 삭제되면 계정은 다시 `미연결` 상태가 되며 팬관리에서 재신청할 수 있다.

# 3-2️⃣ ☕ 카페관리

### 목적
- 카페 운영자가 카페 운영 데이터를 관리하는 전용 탭

### 메인 화면
- 내 카페 목록
- 선택한 카페의 운영 대시보드
- 공지/이벤트 관리
- 홈 배너 관리
- 메뉴/굿즈 관리
- 캐스트/출근표 관리

### 카페 대시보드 내 캐스트 Claim 배치 원칙
- 캐스트 프로필 연결 요청은 별도 서브메뉴로 빼지 않고 `캐스트 관리 섹션` 안에서 처리한다.
- `캐스트 관리 섹션` 제목 바로 아래에 `프로필 연결 요청` 요약 카드를 배치한다.
- `PENDING` 요청이 있을 때만 노출한다.
- 요청 카드는 신청자 활동명, 연결 요청 대상 캐스트명, 신청 시각, 메시지와 `승인 / 반려` 액션을 포함한다.
- 요청이 여러 건이면 최신순으로 최대 3건까지 먼저 노출하고, 이후 `전체 보기`로 확장한다.
- 캐스트 신청 UI는 팬관리 내부에서 처리하고, 카페 대시보드는 운영자 검토/승인 영역으로만 사용한다.
- 캐스트는 이 화면으로 진입하지 않는다.

### 데이터 로딩 원칙
- 카페관리 화면 데이터는 화면별 하드코딩 상태가 아니라 `GetCafeManagementUseCase`를 통해 가져온다.
- `GetCafeManagementUseCase`는 `CafeManagementRepository`를 통해 운영 카페 목록, 검색 가능한 카페 목록, 운영자 신청 상태를 함께 조합한다.
- `CafeManagementRepository`는 `ConCafeDataSource`를 원천 데이터로 사용하고, Repository 내부에 화면용 리스트를 별도 하드코딩하지 않는다.
- 기존 카페 운영자 신청과 신규 카페 등록 신청은 explicit event 패턴으로 목록 화면에 즉시 반영한다.

### 신규 카페 등록 UX 원칙
- `새 카페 등록`은 별도 전용 화면이 아니라 `카페 정보 관리` 입력 폼의 등록 모드를 재사용한다.
- 등록 모드 저장은 카페 문서를 직접 생성하지 않고 `cafeRegistrationClaims`를 생성한다.
- 등록 성공 시 입력 화면은 닫히고, 카페관리 화면의 신청 상태 목록이 즉시 갱신된다.

### 공지/이벤트 관리 UX 원칙
- 카페 운영자는 `공지 및 이벤트 관리` 화면에서 공지사항과 이벤트를 분리된 탭으로 관리한다.
- 목록 조회는 카페별 페이지네이션으로 처리하며 현재 페이지 크기는 15개다.
- 공지/이벤트 작성은 하단 시트에서 수행한다.
- 공지는 제목/내용/고정 여부를 입력하고, 이벤트는 제목/내용/기간/대표 이미지 1장을 입력한다.

### 메뉴/굿즈 관리 상태 원칙
- 메뉴 판매 상태는 `cafes/{cafeId}/menus/{menuId}.isAvailable` 필드를 소스 오브 트루스로 사용한다.
- 굿즈 판매 상태는 `cafes/{cafeId}/goods/{goodsId}.stock` 값으로 판단하며 `stock > 0`이면 판매 중, `0`이면 품절로 본다.
- `메뉴&굿즈 관리` 목록 화면과 편집 화면은 동일한 공용 모델 기준으로 상태를 표시해야 한다.
- 메뉴 추가/수정 저장 시 이름, 가격, 설명, 카테고리와 함께 `isAvailable` 값도 저장한다.
- 굿즈 추가/수정 저장 시 이름, 가격, 이미지, 재고 상태를 함께 저장하며 재고 상태는 `stock`으로 환산한다.
- 메뉴/굿즈 삭제는 목록의 삭제 아이콘을 누른 직후 즉시 반영하지 않고, 확인 다이얼로그/알럿에서 사용자 확인 후 실제 삭제를 수행한다.
- 메뉴/굿즈 추가/수정/삭제 후 목록 화면은 화면 재진입 리로드가 아니라 공용 `observeCafeDetail` 스트림 기준으로 즉시 갱신된다.

### 다중 카페 운영 UX 원칙
- 카페 운영자가 여러 카페를 운영할 수 있으므로 탭 진입 시 먼저 `내 카페 목록`을 노출한다.
- 운영 카페가 1개인 경우에는 목록을 스킵하고 바로 해당 카페의 대시보드로 진입할 수 있다.
- 운영 카페가 2개 이상인 경우에는 카페 선택 후 해당 카페 컨텍스트로 관리 화면을 연다.
- 카페 전환은 상단 드롭다운 또는 `카페 변경` 액션으로 지원한다.
- 연결된 운영 카페가 0개인 경우에는 `카페관리 Empty State`를 노출한다.

### 카페관리 Empty State
- 제목: `아직 연결된 운영 카페가 없습니다`
- 설명: `기존 카페를 검색해 운영 권한을 신청하거나 새 카페를 등록하세요`
- 버튼:
  - 기존 카페 검색
  - 새 카페 등록
- 보조 문구:
  - `운영자 신청은 관리자 승인 후 반영됩니다`

### 기존 카페 검색 화면
- 검색바: 카페명 / 지역 / 주소
- 필터: 국가 / 도시
- 검색 결과 카드:
  - 대표 이미지
  - 카페 이름
  - 지역
  - 승인 상태
  - `이 카페 운영자 신청` CTA

### 운영자 신청 BottomSheet 또는 상세 화면
- 선택한 카페명 확인
- 운영자 신청 메시지 입력
- 운영 증빙 이미지 업로드
- 제출 버튼

### 신청 상태 카드
- `승인 대기 중` 상태 배지
- 신청한 카페 이름
- 신청일
- 처리 안내 문구
- 승인 완료 시 `내 카페 목록으로 이동` 또는 자동 진입
- 반려 시 재신청 CTA 노출 가능

### 내 카페 목록 화면
- 카페 카드 리스트
- 카드 항목: 대표 이미지 / 카페 이름 / 지역 / 승인 상태 / 오늘 체크인 수 요약
- 카드 탭 시 선택한 카페의 관리 대시보드로 이동

### 카페 대시보드 화면
- 오늘 방문자
- 오늘 체크인
- 오늘 리뷰
- 평점
- 빠른 이동: 캐스트 관리 / 출근표 / 이벤트 / 카페 설정 / 홈 배너 관리
- 외부 링크 섹션은 `소속 캐스트 관리`와 `홈 배너 관리` 사이에 배치한다.
- 외부 링크가 1개 이상일 때만 섹션을 노출한다.
- 외부 링크 카드는 제목만 노출하고, 탭 시 앱 내부 `외부 링크 화면(WebView)`으로 이동한다.
- 각 외부 링크 카드에는 삭제 아이콘을 제공한다.
- 현재 구현 단계의 외부 링크 추가/삭제는 대시보드 화면 상태 기준으로 동작하며, shared 영속 저장은 후속 작업이다.

### 카페 정보 수정 화면
- 진입 위치: `카페 대시보드 > 카페 정보 관리`
- 초기값:
  - 카페명
  - 카페 소개
  - 대표 이미지
  - 갤러리 이미지
  - 지역 / 주소
  - 연락처
  - 영업시간
- 데이터 로딩:
  - 화면 초기값은 `GetCafeDetailUseCase`를 통해 가져온다.
  - 별도 화면 하드코딩 초기값은 두지 않는다.
- 저장:
  - 저장 버튼 클릭 시 `UpdateCafeInfoUseCase`를 호출한다.
  - 저장 성공 시 카페 상세 화면과 운영 화면에서 즉시 동일 데이터가 보여야 한다.
  - 저장 성공 피드백은 플랫폼 기본 UX를 따른다.
    - Compose: 스낵바
    - iOS: alert
- 플레이스홀더로 유지 가능한 항목:
  - 대표 이미지 업로드
  - 갤러리 이미지 추가
  - 지도 핀 위치 조정
  - 예외 영업일 관리

### 홈 배너 관리 화면
- 배너 목록 탭: `진행중`, `예약`, `종료`
- + 배너 등록 버튼
- 각 배너 카드에 썸네일, 제목, 노출 기간, 상태, 연결 대상 표시
- 슬롯 초과 상태에서는 등록 버튼 클릭 시 `즉시 게시 불가 / 예약 등록만 가능` 안내 노출
- 현재 선택한 카페 기준으로 연결 가능한 대상만 노출한다.

### 카페 운영자 배너 등록 플로우
1. 배너 이미지 업로드
2. 제목 / 서브 문구 입력
3. 연결 대상 선택 (선택한 카페 상세 / 이벤트 / 공지 / 외부 링크)
4. 노출 기간 슬라이더 선택 (1일 ~ 10일)
5. 저장
6. 활성 슬롯 여유가 있으면 `ACTIVE`, 없으면 `SCHEDULED`로 등록

### 배너 연결 대상 UX 원칙
- `카페 상세`는 운영자의 현재 카페 컨텍스트를 기본 적용값으로 사용한다.
- `공지사항`, `이벤트 상세`는 관리자만 카페를 직접 선택할 수 있다.
- 운영자는 본인 운영 카페 기준으로만 공지/이벤트를 검색하고 선택한다.
- `외부 링크`만 URL 직접 입력 방식을 사용한다.
- 홈에서 외부 링크 배너를 누르면 외부 브라우저가 아니라 앱 내부 `외부 링크 화면(WebView)`으로 이동한다.

### 캐스트 상세 후기 노출 원칙
- 캐스트 상세 화면에는 별도 `캐스트 리뷰`를 만들지 않는다.
- 캐스트 상세 화면 후기 섹션은 `함께 언급된 후기` 또는 `태그된 카페 리뷰`로 표기한다.
- 노출 대상은 `cafes/{cafeId}/reviews/{reviewId}` 중 `taggedCastIds[]`에 현재 캐스트 id가 포함된 카페 리뷰다.
- 이 후기의 평점은 캐스트 평점이 아니라 카페 리뷰 평점이다.

### 공식 SNS 노출 규칙
- 캐스트 상세 화면에는 캐스트가 등록한 외부 SNS 링크를 아이콘 또는 링크 버튼 형태로 노출한다.
- 노출 대상 플랫폼 예시:
  - Instagram
  - X
  - TikTok
- 외부 링크가 없는 경우 해당 섹션은 숨기거나 빈 상태를 노출하지 않는다.
- 링크 탭 시 외부 브라우저 또는 플랫폼 앱으로 이동한다.

# 🏪 Multi-Cafe Owner 구조 설계

ConCafe에서는 하나의 카페 운영자가 여러 카페를 운영할 수 있다.

예시

Owner A
- Maid Dream Tokyo
- Seoul Maid Cafe
- Akihabara Butler Cafe

따라서 Owner와 Cafe의 관계는 다음과 같다.

Owner (1) → Cafe (N)

### Firestore 구조

users/{userId}

- role: VISITOR | CAST | CAFE_OWNER | ADMIN
- ownedCafeIds: [cafeId]

cafeOwnerClaims/{claimId}

- userId
- cafeId
- status
- message
- evidenceImageUrls[]
- reviewedAt

cafes/{cafeId}

- name
- description
- ownerIds: [userId]
- createdAt
- approved

ownerIds는 여러 운영자를 지원하기 위해 배열 구조로 설계한다.

예시

cafes/{cafeId}

- ownerIds:
  - ownerA
  - ownerB

이 구조는 공동 운영이나 지점 관리 상황에서도 유연하게 동작한다.

### UX 적용 원칙

- 카페 운영자는 앱 진입 후 자신이 관리하는 카페 목록을 먼저 확인한다.
- 운영 카페가 여러 개여도 하단 탭은 하나의 `카페관리` 탭만 사용한다.
- 세부 관리 기능은 선택된 카페 컨텍스트 안에서 동작한다.
- 연결된 운영 카페가 없을 경우에는 기존 카페 검색 또는 신규 카페 등록을 유도하는 빈 상태 화면을 사용한다.

## Cast Management

카페에 소속된 캐스트 관리 기능

가능 기능

- 캐스트 추가
- 캐스트 프로필 수정
- 캐스트 사진 업로드
- 캐스트 스케줄 등록
- 캐스트 외부 SNS 링크 관리

### 캐스트 프로필 편집 상태 원칙
- `캐스트 프로필 추가`와 `캐스트 프로필 수정`은 동일한 편집 화면을 사용한다.
- 수정 화면 초기값은 프레젠테이션 하드코딩이 아니라 공용 `GetCastDetailUseCase` 결과로 로드해야 한다.
- 저장은 공용 `UpsertCastUseCase`를 통해 처리하고, Android Compose와 iOS SwiftUI가 동일한 입력 검증과 성공/실패 흐름을 사용해야 한다.
- 캐스트 기본 정보 저장 범위는 이름, 컨셉 역할, 생일, 소개, 근무 요일이다.
- 근무 요일 선택은 캐스트 문서의 별도 배열 필드가 아니라 `castSchedules` 문서 생성/갱신 기준으로 관리한다.
- 프로필 사진 업로드, 갤러리 업로드, 외부 SNS 링크 CRUD는 후속 단계에서 연결한다.

### Firestore

cafes/{cafeId}/casts/{castId}

- name
- profileImage
- description
- birthday
- joinDate

cafes/{cafeId}/casts/{castId}/externalLinks/{linkId}

- platform
- title
- url
- isVisible
- sortOrder

### 화면 구성

- 캐스트 목록 카드
- `캐스트 추가` 버튼
- 캐스트 편집 진입
- 최근 스케줄 요약
- 캐스트 편집 화면에서 외부 SNS 링크 추가 / 수정 / 삭제
- 현재 MVP 구현 범위에는 캐스트 프로필 추가/수정 공용 화면과 shared mock 데이터 저장까지 포함한다.
- 현재 단계의 저장 성공 시 캐스트 상세 화면에서 다시 진입하면 수정값이 동일하게 로드되어야 한다.
